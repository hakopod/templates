# Catalog completion review, 24 September 2026

The requested Dokploy pages were treated as discovery references, then compared
with upstream image manifests, pinned container configuration and application
source. Docker Compose syntax alone did not establish a usable Hakopod deployment.

| Entry | Original gap | Native implementation |
| --- | --- | --- |
| Dagu | Root/sudo image entrypoint | Direct unprivileged scheduler/UI command, basic authentication and persistent home |
| CouchDB | Missing explicit single-node initialization | Private authenticated HTTP, single-node file config, stable cookie secret and data PVC |
| Cal.com | Hardcoded example database password, root-owned URL substitution and ignored migration failures | Private database connection bindings, three generated secret references and a digest-pinned non-root compatibility image built from public source |
| Blinko | Uploaded files omitted from persistence; startup ignored migration failures | PostgreSQL plus .blinko PVC, scoped database binding, fail-fast startup and bounded temporary exports |

| Autobase | Docker socket, host Ansible directory and root initialization required | Concrete native candidate records ports, secrets and storage, but remains blocked from tenant deployment |

These are new-install presets. Updating a catalog image is not a database upgrade
or customer data migration. Third-party commercial features remain under their
own licenses; Hakopod Pro does not license upstream applications.

## Other incomplete entries

The earlier catalog has explicit migration guides for Dify, Supabase, Rocket.Chat,
Xem, Vault and other applications. They are intentionally rejected by the deploy
API. Their candidate TOML is not a promise of working installation. This pass did
not promote them merely because lifecycle/file-mount support is now available.
The detailed blockers remain in each blueprint's migration.json and README.
Further promotion requires the same concrete checks: current image digest and
architecture, full dependency topology, non-root bootstrap, application secret
requirements, storage/recovery and actual named-cluster acceptance.

## Evidence boundaries

`images.lock.json` records remote registry inspections. Catalog validation checks
metadata/TOML secret references, including bindings and file secrets. Engine
contract tests cover private dependencies, non-root commands, persistent paths
and provider-secret generation rules. The dedicated complete-catalog workflow
runs each application alone in a named disposable development cluster, with a
bounded 6 GiB server and at most two independent runner jobs. Dagu/CouchDB access,
PVC restart persistence and Baserow media read/write through a real disposable
MinIO service are checked where applicable. A MinIO test is not proof that every
S3 provider's TLS, CORS or policy is configured correctly.

The Cal.com image workflow separately checks that UID 1000 can replace the public
URL and run installed migration/seed binaries. Only a successful real application
startup can establish its runtime acceptance; a wrapper build alone cannot.

No customer deployment, database, volume or provider bucket was changed for this
review. Actual CI results should be appended here after execution.

## Verified runtime checks

Workflow [36012352984](https://github.com/hakopod/hakopod/actions/runs/36012352984)
passed both AMD64 and ARM64 jobs for Dagu, CouchDB, Blinko and Bytebase.
